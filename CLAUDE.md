# Rules for Claude

Reusable rules for any project. Projects carry no `CLAUDE.md`: these rules are the only ones
for Claude, and they change here. Project-specific rules (names, physics, conventions) are in
each project's developer guide, for humans and Claude alike: read it before working on a
project.

## Git workflow

- Explicit, descriptive branch names (`fix/core-math`, `doc/user-manual`), one topic per branch.
  Branches are stacked: each new branch starts from the current tip.
- Never rewrite published history: no rebase, amend or force-push of pushed branches. Reconcile
  parallel stacks with merge commits.
- Commits are in my name (the repository's git config), with the Claude attribution trailer.
- No pull requests unless I ask for one.
- Validate locally before every push (build with every supported compiler, in Debug and in
  Release, warnings as errors, full test suite, linters, type checker), then confirm the push
  (`git rev-parse` of the remote branch) and give me the tip branch to pull.
- When other projects push branches here, check that they stack or merge cleanly, build them
  and run the tests, fix what breaks in a separate commit, and say which branch is the tip.

## Reviews

- Review branch by branch, and file by file, so that we can discuss each file separately.
- For a long review, prepare one markdown file per branch, to go through the changes file by
  file (possibly with a smaller model). Review notes live on an orphan branch (`review/notes`).
- Fixes I only note during a review are applied at the end, in a finalization plan that also
  carries my new requests.

## Audits

- Before starting, settle two things with me: the scope (numerics and physics correctness, the
  Python API and bindings, build and CI, documentation and code quality) and the delivery
  (report then fix on approval, report only, or fix as I go: one commit per finding).
- Read every file in scope in full. Agents may map the tests against the code (what each test
  exercises, what no test exercises, where code and comments disagree, suspicious arithmetic
  with file:line), but the judgement is yours: read the code yourself.
- A finding is confirmed only when it is reproduced: a numerical experiment against the built
  library (scratch programs outside the repository, never committed), a measured convergence
  order, a failing input. A suspicion that does not reproduce is not reported as a bug; what was
  checked and found correct is listed too, so that the audit is a record.
- Do not trust reference values that were generated from the code under test: check physical
  constants and closed forms against an independent source (a standard atmosphere value, a
  textbook table, a legacy implementation).
- Watch for the tests that hide a bug: a test function with a symmetry that cancels the leading
  error term (`sin` on `[0, pi]` for an integration rule), an assertion that passes vacuously when
  both results fail, a tolerance that masks the convergence order.
- Fix each confirmed finding in its own commit, with a regression test that fails before and
  passes after. The commit message says what was wrong, how it showed, and what changed. Validate
  each commit like any push (every compiler, warnings as errors, full tests, linters, docs).
- Decisions that are not mine to take go to me as a question: a physical constant, a scheme kept
  identical to another project's implementation versus a more accurate one, an API change. The
  default is the smallest change that makes the code match its documentation; when the code is
  right and the documentation wrong, fix the documentation and add a test that pins the claim.
- Validation holes (NaN passing a sign test, a non-increasing mesh dividing by zero, a parameter
  that makes a quantity infinite) are findings: the function must fail explicitly, with a message
  naming the input, never return NaN or a misleading message from deep inside a solver.
- Report by impact: wrong results or crashes first, then accuracy and robustness, then the list
  verified correct, then what was reported but not changed (API changes go to the roadmap).
  Every finding names the file and line, the reproduction, and the fix.

## Python

- Python ≥ 3.12. Type aliases are `type X = ...` statements, never `X: TypeAlias = ...`.
- The code runs with the oldest versions of the cluster modules (e.g. NumPy 1.26, scipy 1.12):
  no argument or function that only newer versions have; test with those versions.
- ruff (lint and format) and basedpyright with its default (strict) configuration: 0 errors,
  0 warnings.
- A library exposes the types its clients need in a `typing.py` module (aliases, protocols,
  result types). Logging helpers go in `logging.py` (not `log.py`).
- Compiled modules ship type stubs, checked by a test against the compiled module. The stubs are
  generated by one pinned toolchain (e.g. pybind11 and pybind11-stubgen as submodules), since
  another version gives different stubs.

## C++

- C++20. Private members get a trailing underscore (`value_`); public members and parameters
  don't.
- Low-level functions take plain floating-point values (`real`, radians...); wrapper types (e.g.
  `Angle`) are for the user-facing API.
- Overload rather than multiply function names, when the semantics are the same.
- Reuse the libraries the project already depends on (e.g. std_e for logging and printing)
  before writing a helper; audit them before adding a dependency.
- Numerical or physical failures return a result (value, status, iterations, message) rather
  than throwing; exceptions are for programming errors.

## Tests and documentation

- Unit tests live next to their sources (`*.test.cpp`, `test/test_*.py`).
- Documentation code snippets also live next to their sources (`<topic>.snippet.cpp`,
  `test/snippet_<topic>.py`), are run by the test suite, and are included in the docs with
  `literalinclude` markers. No separate `cpp/` / `python/` snippet tree.
- The documentation build is a test (Sphinx `-W --keep-going`, fresh environment).
- The developer guide has a checklist for a new file or function: tests, bindings, stubs,
  `__all__`/`typing.py`, docstrings, API page, user-manual section, release notes, roadmap,
  checks with every compiler.
- The user manual documents every feature, theory and usage together: equations, method, order
  of accuracy, limits and failure statuses, a tested example, and references. Every formula is
  checked against the code, never written from memory.

## Build and dependencies

- Code and tool dependencies are git submodules in `external/` (e.g. `external/pybind11`,
  `external/pybind11-stubgen`). Documentation dependencies (Sphinx, themes, extensions) are
  the `doc` dependency group of `pyproject.toml`, installed in a venv (not submodules: an
  extension can carry symlinks into submodules of its own).
- Development tools are optional: a test that needs a missing tool is not registered (with a
  CMake warning), so that the rest still runs.
- Deployment uses modulefiles; testing uses the `source.sh` that project_utils writes in the
  build directory.

## GitLab CI (cluster)

- The build and test environment comes from the loaded modules, no virtual environment. I
  update the module versions myself. The exceptions are `job:lint` (ruff and basedpyright) and
  `job:doc` (the `doc` dependency group): a temporary venv (`--system-site-packages`, from the
  loaded python3).
- Layout: `.gitlab-ci.yml` includes `.gitlab/ci/{common,init,build,test,quality,doc}.yml`
  (see `templates/gitlab-ci/`). `job:init` clones manually into a shared workspace and passes
  the paths as a dotenv artifact. `job:build` configures and builds once, with all tests
  enabled. Test jobs only select subsets with `ctest -R` (never reconfigure).
- Stages `init, build, test, quality, doc, deploy`. The real tests are in `test` and fail red.
  Checks that depend on optional tools (stubs, lint) are in `quality`, and exit with
  code 3 (an allowed failure, orange) when a tool is missing, so that the `test` stage reads
  green or red at a glance. `job:lint` exits with code 4 (orange too) on findings, published
  as a GitLab Code Quality report (`.gitlab/ci/merge_codequality.py` merges the tools' reports).
- Check the YAML before pushing (`tools/check_ci.py`): an unquoted `: ` in a script line turns
  it into a mapping.

## Official repository and GitHub copy

- The official repository (e.g. GitLab) and its GitHub copy (where Claude works) share no
  history: files are copied raw, with no git trace, by `tools/sync_project.sh`, with the
  layout `project/<name>` (official) and `project/gh/<name>` (GitHub).
- Work happens on GitHub branches; the tip branch is then deployed to the official repository
  (`sync_project.sh --apply <name> to-official origin/<tip>`), and committed there by me.
- Links in the docs and package metadata point to the official repository.
- The step-by-step workflow and the submodule handling (`tools/git-pin-submodule`) are in
  `doc/official_and_github.md`.
